Set up AWS federated identity for Entra app tokens

This guide shows development teams how to replace client_secret or certificate authentication with a Federated Identity Credential (FIC).

Your AWS-hosted workload requests a short-lived JWT from AWS IAM Outbound Identity Federation. It sends that JWT to the Microsoft identity platform as client_assertion.

Entra ID validates the JWT against a pre-configured FIC on your app registration. If validation succeeds, Entra ID issues an access token.

Important This change affects workload-to-Entra authentication only. It does not change your users’ browser sign-in experience.

Security requirement Do not log JWTs or access tokens. Log metadata only, such as issuer and subject.

Prerequisites

You must have all of the following:

  1. An existing Entra app registration managed in the https://github.com/ministryofjustice/staff-identity-idam-entra-infra GitHub repository.
  2. An AWS IAM role for your workload, such as Lambda, ECS task, or EC2 instance profile.
  3. A Pull Request containing a Terraform change for a Federated Identity Credential.

Understand what changes

Area Current approach Federated approach
Backend token request Send client_secret or certificate assertion Send client_assertion JWT from AWS
Credential storage Secret or certificate in code, CI/CD, or secret store No long-lived secret in app code or pipeline
Rotation burden Manual secret or certificate rotation JWT is short-lived and requested on demand
Customer sign-in flow OAuth2 user sign-in in browser No change

Step 1: Enable AWS outbound identity federation

  1. In AWS Console, go to IAM, then Access Management, then Account Settings.
  2. Enable Outbound Identity Federation.
  3. Record the Token Issuer URL.
  4. Identify the IAM role your workload runs as.
  5. Confirm the exact JWT sub value your workload will present.

Step 2: Request Entra trust configuration

Raise a request to the Entra Platform Team through your normal Terraform process.

Provide the following values:

Detail to provide Example
AWS Outbound Identity Federation Token Issuer URL https://<your-account-outbound-federation-url>
Subject claim (sub) your workload will present Environment-specific role or session subject
AWS Environment dev, staging, prod

Request one FIC per environment.

The Platform Team configures a Federated Identity Credential on your app registration with issuer and subject.

Step 2a: Update your IDAM Terraform for app registration federation

If your application registration is managed in the DISO IDAM https://github.com/ministryofjustice/staff-identity-idam-entra-infra repo, add a federated_identity_credentials block to the application registration definition.

Use AWS values from IAM Outbound Identity Federation.

The key values from AWS are:

  1. Token Issuer URL from IAM Account Settings.
  2. Subject claim (sub) that your workload role or session presents.

Use this Terraform pattern:

federated_credentials = [
  {
    display_name = "aws-prod-workload"
    issuer       = "https://<aws-outbound-federation-issuer-url>"
    subject      = "<exact-aws-jwt-sub-claim>"
    audiences    = ["api://AzureADTokenExchange"]
  },
]

Set the values as follows:

  1. Set display_name to a unique, readable name per environment.
  2. Set issuer to the AWS Outbound Identity Federation Token Issuer URL.
  3. Set subject to the exact JWT sub value from your AWS workload identity.
  4. Set audiences to api://AzureADTokenExchange unless your platform team instructs otherwise.

For production, prefer strict subject matching and avoid broad wildcard trust.

Security requirement Keep trust as narrow as possible. Only trust the exact AWS issuer and subject needed for the workload.

Step 3: Update your token request code

Replace code that loads a client secret or certificate with code that:

  1. Requests a signed JWT from AWS Outbound Identity Federation.
  2. Sends that JWT to Entra as client_assertion.

Use the standard OAuth2 client_credentials grant with assertion fields.

Token endpoint

POST https://login.microsoftonline.com/<tenant-id>/oauth2/v2.0/token
Content-Type: application/x-www-form-urlencoded

Request parameters

grant_type=client_credentials
&client_id=<your-app-client-id>
&scope=<scope, e.g. https://graph.microsoft.com/.default>
&client_assertion_type=urn:ietf:params:oauth:client-assertion-type:jwt-bearer
&client_assertion=<the JWT issued by AWS Outbound Identity Federation>

Example (Node.js)

const awsJwt = await getAwsOutboundFederationToken(); // your AWS SDK call

const params = new URLSearchParams({
  grant_type: "client_credentials",
  client_id: process.env.ENTRA_CLIENT_ID,
  scope: "https://graph.microsoft.com/.default",
  client_assertion_type:
    "urn:ietf:params:oauth:client-assertion-type:jwt-bearer",
  client_assertion: awsJwt,
});

const res = await fetch(
  `https://login.microsoftonline.com/${process.env.TENANT_ID}/oauth2/v2.0/token`,
  { method: "POST", body: params }
);

const { access_token } = await res.json();
// No secret or certificate referenced anywhere above.

Example (Python)

import requests

aws_jwt = get_aws_outbound_federation_token()  # your AWS SDK call

resp = requests.post(
    f"https://login.microsoftonline.com/{TENANT_ID}/oauth2/v2.0/token",
    data={
        "grant_type": "client_credentials",
        "client_id": ENTRA_CLIENT_ID,
        "scope": "https://graph.microsoft.com/.default",
        "client_assertion_type":
            "urn:ietf:params:oauth:client-assertion-type:jwt-bearer",
        "client_assertion": aws_jwt,
    },
)

access_token = resp.json()["access_token"]

If you already use MSAL, use a client assertion callback where available. Method names vary by SDK version and language.

Step 4: Validate in non-production

  1. Deploy to a non-production environment.
  2. Confirm the workload retrieves a JWT from AWS outbound identity federation.
  3. Confirm the token exchange with Entra succeeds and returns an access token.
  4. Confirm normal application behavior works with the new token.
  5. Confirm no secret or certificate is required in runtime configuration.

Compliance note Validate each environment independently. Do not assume prod matches dev or staging.

Step 5: Remove old secrets safely

After successful validation per environment:

  1. Remove client secret or certificate references from code.
  2. Remove related environment variables and secret manager entries.
  3. Ask the Platform Team to delete old secret or certificate credentials from the app registration.
  4. Keep production secret fallback until production validation is complete.

Troubleshooting

Error or symptom Likely cause What to check
AADSTS700021 invalid client_assertion JWT sub does not match FIC subject Decode JWT and compare sub exactly with configured FIC subject
Issuer or discovery errors Outbound federation disabled or wrong issuer URL Re-check AWS IAM Account Settings Token Issuer URL
Works in dev but not prod Different AWS account or role without matching FIC Confirm separate FIC exists for production issuer and subject
Intermittent token failures JWT expired before use or clock skew Request JWT immediately before token exchange and verify token times

Operational note Entra ID caches only the first 100 signing keys from an external OIDC endpoint. This is not expected to be a practical issue with AWS issuers, but include it in diagnosis if validation behavior changes.

Frequently asked questions

Does this change how customers sign in?

No. Customer-facing browser sign-in flows stay the same.

Can we keep secrets during migration?

Yes. Keep existing secret or certificate during migration and remove it after validation.

Do we need one Federated Identity Credential per environment?

Yes, in most cases. Each environment typically has a different AWS account, role, or subject claim.
